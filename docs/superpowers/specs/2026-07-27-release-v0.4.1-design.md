# Release v0.4.1 — Design

**Branch:** `20260727-release-v0.4.1`
**Base:** `master` @ `0.4.0`
**Date:** 2026-07-27
**Status:** Awaiting review

## Background

A single fix landed on the release branch off `master@0.4.0`: issue 41 — the Anthropic tokenizer was being repeatedly invoked during context processing, causing high CPU usage and TUI stalls on long sessions. The fix removes the Anthropic tokenizer dependency and restores the lightweight character-based per-message token estimator in `src/utils/tokens.ts`.

`pnpm check` is green (48 files, 368 tests). `dcp.schema.json` is unchanged. The branch contains exactly one merged code change (`50e4209`) — no API surface change, no new features, no schema drift. The release is a pure patch.

## Problem

Two user-facing documents (`README.md` and `CHANGELOG.md`) currently claim that v0.4.0 introduced the Anthropic tokenizer as the token-counting engine. That claim is now false (the dependency was actually introduced and then removed in this patch release). Shipping the patch without correcting those docs leaves the repository in an internally inconsistent state where:

- The README's `## What's new in 0.4.0` advertises a feature that no longer exists.
- The CHANGELOG's `## [0.4.0]` entry lists the same non-existent change under `### Changed`.

A 0.4.0 user reading the release notes after upgrading to 0.4.1 would expect Anthropic-tokenizer behavior they do not get.

## Goals

1. Tag the issue 41 fix as v0.4.1 so users on a clean 0.4.0 install pick up the patch.
2. Correct the documentation so neither file describes the Anthropic tokenizer as the current implementation.
3. Keep the user-facing changes minimal — this is a patch release, not a release-notes overhaul.

## Non-goals

- Rewriting the 0.4.0 release notes beyond deleting the one inaccurate bullet.
- Adding a long-form migration guide (no API change occurred).
- Reordering, regrouping, or reformatting other bullets.
- Code changes of any kind (already merged).
- Tagging or publishing (the user triggers these explicitly).

## Approach

Three files, three commits, no code changes.

### File 1 — `package.json`

Single-line change:

```diff
-  "version": "0.4.0",
+  "version": "0.4.1",
```

### File 2 — `CHANGELOG.md`

Convert the existing `[Unreleased]` block into the `0.4.1` release entry, and drop the misleading 0.4.0 bullet.

Before:

```md
## [Unreleased]

### Fixed

- Long sessions no longer repeatedly invoke the Anthropic tokenizer during context processing, preventing high CPU usage and TUI stalls.

## [0.4.0] - 2026-07-08

### Changed

- Token counting now uses the Anthropic tokenizer with fallback behavior, improving context and pruning estimates.
```

After:

```md
## [0.4.1] - 2026-07-27

### Fixed

- Long sessions no longer repeatedly invoke the Anthropic tokenizer during context processing, preventing high CPU usage and TUI stalls.

## [0.4.0] - 2026-07-08

### Changed
```

The 0.4.0 entry retains all other bullets verbatim (compression notifications, `dcp:permission`, `turnProtection`, TypeBox-derived config, the two `### Fixed` entries). Only the inaccurate `Token counting now uses the Anthropic tokenizer...` line is removed.

### File 3 — `README.md`

Two changes inside the user-facing release-notes section.

**Change A — drop the inaccurate 0.4.0 bullet.**

Before:

```md
## What's new in 0.4.0

- Compression notifications can now surface summary text with `compress.showCompression`.
- `dcp:permission` adds runtime control over compress-tool usage.
- Deduplication can preserve recent duplicates via `turnProtection`.
- Token counting now uses the Anthropic tokenizer for better sizing estimates.
- Config validation and the shipped `dcp.schema.json` now come from the same TypeBox source of truth.
```

After:

```md
## What's new in 0.4.0

- Compression notifications can now surface summary text with `compress.showCompression`.
- `dcp:permission` adds runtime control over compress-tool usage.
- Deduplication can preserve recent duplicates via `turnProtection`.
- Config validation and the shipped `dcp.schema.json` now come from the same TypeBox source of truth.
```

**Change B — add a small `## What's new in 0.4.1` section immediately after.**

```md
## What's new in 0.4.1

- Long sessions no longer repeatedly invoke the Anthropic tokenizer during context processing.
- Per-message token estimates are restored to the lightweight character-based heuristic.
```

Inserted between `## What's new in 0.4.0` and `## Development and verification`. No other section of the README changes.

### Commit strategy

Three commits, each scoped to one file, in this order:

1. `chore: bump version to 0.4.1` — `package.json`.
2. `docs(changelog): release 0.4.1` — `CHANGELOG.md`.
3. `docs(readme): update release notes for 0.4.1` — `README.md`.

This matches the repo's existing release-prep style and keeps each commit independently reviewable and revertable.

### Tag and release

Out of scope. The user explicitly owns the `git tag v0.4.1` and `pnpm publish` steps; the assistant will not execute them without a separate go-ahead.

## Alternatives considered

- **Skip the README addition entirely.** Tempting, but the only accurate way to document a patch release is to mention it. Two short bullets are the minimum that lets a reader understand what changed and why. Rejected.
- **Rewrite the 0.4.0 block to say "token counting reverted from Anthropic tokenizer."** More thorough, but it implies 0.4.0 shipped the Anthropic tokenizer as a deliberate feature — it did not, it was an accidental regression that was caught quickly. Best left undiscussed. Rejected.
- **Bump to 0.5.0 because the tokenizer change is "semver-major."** No public API or config schema changed; the lightweight heuristic was the original implementation before 0.4.0; this is restoring prior behavior. Patch is correct. Rejected.
- **Squash all three files into one commit.** Splits user-visible diff (release notes) from the machine-readable version bump, harder to audit. Rejected in favor of three commits.

## Risks

- **Wrong version number.** Mitigation: branch is named `20260727-release-v0.4.1`; user explicitly chose 0.4.1 during brainstorming to match the issue 41 spec's stated intent.
- **Inadvertent code or schema drift.** Mitigation: `pnpm check` must stay green; `git diff --exit-code -- dcp.schema.json` must be empty after the edits.
- **README section order inconsistency.** Mitigation: `## What's new in 0.4.1` placed immediately after `## What's new in 0.4.0`, preserving the existing descending-version pattern.

## Verification

After applying the three edits and committing:

1. `pnpm check` — must report zero errors (was already green; verify no regression).
2. `git diff master -- dcp.schema.json` — must be empty.
3. `git diff master -- src/` — must be empty (no code changes beyond the already-merged `50e4209`).
4. `git log master..HEAD --oneline` — must show exactly four commits: the original `50e4209` (issue 41 fix) plus the three release-prep commits.
5. `grep '"version"' package.json` — must print `"version": "0.4.1",`.
6. `grep -A1 '## What's new in 0.4.1' README.md` — must show the new two-bullet section.
7. `grep 'Anthropic tokenizer' README.md CHANGELOG.md` — must return zero hits in `README.md` and zero hits inside `## [0.4.0]` in `CHANGELOG.md` (only the new `## [0.4.1]` entry should match).

## Definition of done

- All three files modified as specified.
- Three release-prep commits added on top of `50e4209`.
- All seven verification checks pass.
- User has reviewed and approved this spec.
- Tagging and publishing remain user-driven.
