# Release 0.4.0 Prep Design Spec

Prepare the next `pi-dcp` release by updating package metadata and user-facing documentation to match the code already merged since `0.3.0`.

This spec covers a release-prep pass only. It does **not** include runtime code changes unless review uncovers a release-blocking mismatch between shipped behavior and published docs.

---

## Resolved Design Decisions

| Decision            | Resolution                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------------- |
| Target version      | Bump `package.json` from `0.3.0` to `0.4.0`.                                                                    |
| README audience     | End users first. Lead with install, commands, workflows, and usage.                                             |
| Changelog style     | Curated release notes, not a commit-by-commit replay.                                                           |
| README config depth | Full option reference plus examples.                                                                            |
| Scope boundary      | Only `package.json`, `CHANGELOG.md`, and `README.md` change unless a blocking docs/code mismatch is discovered. |

---

## Goals

1. Publish the next release as `0.4.0`.
2. Describe the meaningful user-visible changes shipped after `0.3.0`.
3. Rewrite the README so users can install, operate, and configure `pi-dcp` without reading the source.
4. Keep the diff surgical and avoid mixing release-prep with new feature work.

## Non-Goals

- No new runtime features.
- No refactors, schema edits, or test rewrites.
- No retroactive changelog cleanup for older releases.
- No expansion of planning docs beyond this spec and its follow-up implementation plan.

---

## Current State Summary

The repo is already past `0.3.0` in actual shipped functionality. Recent commits since that release added or completed:

- compression notifications and `compress.showCompression`
- runtime `dcp:permission` toggling
- deduplication `turnProtection`
- Anthropic tokenizer-based token counting
- TypeBox-backed config validation
- generated `dcp.schema.json`

`README.md` and `CHANGELOG.md` do not yet present that full post-`0.3.0` surface area clearly enough for release.

---

## Proposed Approach

Use a usage-first release-prep pass:

1. **Bump version metadata** in `package.json` to `0.4.0`.
2. **Add a curated `0.4.0` changelog entry** focused on user-visible additions, behavior changes, and notable reliability fixes.
3. **Rewrite `README.md`** around end-user tasks first, while preserving a complete configuration reference.

This is the smallest durable change that makes the repo publish-ready.

---

## File-Level Design

### 1. `package.json`

**Change:**

- Update `version` from `0.3.0` to `0.4.0`.

**Why:**

- The merged work since `0.3.0` is a minor release, not a patch. It added multiple new config options, commands, and user-visible behaviors.

**Out of scope:**

- No dependency changes unless already required by documentation verification.

### 2. `CHANGELOG.md`

**Change:**

- Insert a new `## [0.4.0] - 2026-07-08` section above `0.3.0`.

**Structure:**

- `### Added`
- `### Changed`
- `### Fixed` (only if the fixes are meaningfully user-visible)

**Content priorities:**

- Mention features users can discover or configure now:
  - `compress.showCompression`
  - `dcp:permission`
  - deduplication `turnProtection`
  - generated `dcp.schema.json`
- Mention meaningful behavior changes:
  - Anthropic tokenizer-backed token counting
  - TypeBox-backed config validation and defaults behavior
- Skip low-signal noise:
  - planning doc commits
  - merge mechanics
  - purely internal commit choreography

**Tone:**

- Release-note style, concise, user-facing.

### 3. `README.md`

**Change:**

- Rewrite the document with end-user usage as the top priority.

**Planned structure:**

1. One-paragraph overview
2. Install
3. Local development / local checkout tryout
4. Quick start
5. Commands table
6. Typical workflows
7. Configuration
8. What's new in `0.4.0`
9. Development and verification
10. Changelog / license links

**Required README coverage:**

- `dcp:permission` command in the command list and workflow examples
- updated config example including:
  - `compress.showCompression`
  - `strategies.deduplication.turnProtection`
  - `nudgeNotificationType`
  - absolute token limits and percentage-string behavior
- mention `dcp.schema.json` as a generated schema users can reference
- practical examples first, but still include a full option reference

**What to de-emphasize:**

- internal architecture details
- implementation history
- long contributor discussion in the top half of the file

## Release Narrative

The release should read as a documentation catch-up to a meaningful feature increment rather than a generic maintenance bump.

### Main user story

`pi-dcp` now gives users better operational control and clearer configuration:

- better visibility into compression behavior
- a runtime way to allow/deny compression
- safer duplicate pruning through turn protection
- more accurate token accounting
- a clearer configuration contract via TypeBox validation and generated schema

The README and changelog should make that story obvious within the first screenful.

---

## Verification Plan

This is a docs/metadata pass, so verification should stay narrow:

1. Confirm `package.json` version is `0.4.0`.
2. Cross-check README command names against current registered commands.
3. Cross-check README config keys against current config schema and defaults.
4. Confirm `CHANGELOG.md` describes only work actually present in the codebase after `0.3.0`.
5. If documentation changes expose possible drift, run the cheapest meaningful verification command:
   - `pnpm run generate:schema` when schema/docs alignment is in doubt
   - `pnpm release:check` only if broader release confidence is needed

Verification should prove the docs match the code, not reopen implementation work.

---

## Risks And Mitigations

| Risk                                                      | Mitigation                                                                                                   |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| README claims commands or config that drifted from source | Cross-check against `src/commands/*`, `src/config-schema.ts`, and `dcp.schema.json` before finalizing edits. |
| Changelog overstates internal work as user-visible value  | Keep entries curated and tied to actual user-facing behavior.                                                |
| Release-prep turns into unplanned code work               | Hold scope to three files unless a release-blocking mismatch is discovered.                                  |

---

## Definition Of Done

This release-prep spec is satisfied when:

- `package.json` is bumped to `0.4.0`
- `CHANGELOG.md` contains a curated `0.4.0` entry
- `README.md` is rewritten for end-user usage and reflects the current feature/config surface
- verification shows the docs match the current codebase
- no unrelated runtime or refactor work is mixed into the release-prep diff
